# 링크모아 (link-moa) 가설·검증 설계

날짜: 2026-07-20
상태: 검토중
관계: `2026-07-14-link-moa-mvp-design.md`(풀 MVP, Path 1 가정)를 만들기 **전에** 칠 검증.
MVP 문서는 그대로 두고, 이 문서는 "그 앱을 지을 가치가 있는지" 먼저 확인하는 실험 설계다.

---

## 1. 왜 이 문서인가

기존 MVP 설계는 **하나의 해법**(공유 저장 + 카테고리 + 안 본 탭 + 알림)이지 **검증**이 아니다.
풀 iOS 앱(공유 익스텐션 + SQLite + 알림 + TestFlight)을 다 만드는 건 "가설을 확인"하기엔 비싸다.
그래서 코드 한 줄 짜기 전에, 가장 위험한 가정을 가장 싸게 친다.

이 아이디어 밑에 깔린 핵심 위험은 **collector's fallacy**다:
저장하는 행위 자체가 만족감을 줘서, 정작 다시 보지 않는다. "못 찾는 불편"보다
"애초에 다시 안 보는" 게 더 근본 문제일 수 있다.

---

## 2. 겨냥하는 불편 (Pain)

사용자가 실제로 아파한다고 본 불편(본인 셀프-부검으로 지목):

```
P2 흩어져 있음 (근본 원인)
   ├─▶ P3 필요할 때 못 찾음   (급성 증상: 지금 필요한데 어디 있는지)
   └─▶ P4 까먹어서 못 씀       (만성 증상: 필요한 줄도 모르고 지나감)
```

**정밀화한 통증 모델:**
> 필요한 순간(P3 트리거)은 취미·일·자기계발 등 넓게 온다.
> 그런데 "저장했다는 사실"을 못 떠올려서(P4) 다시 확인을 못 한다.
> **즉 P4는 별개 불편이 아니라 P3 실패의 원인이다.**

**아직 불확실한 지점(= 테스트할 이유):**
- P4가 진짜 "불편"인가, 아니면 "안 봐도 안 아쉬운" 것(collector's fallacy)인가?
  → 셀프-부검에선 "잊었지만 지금 보니 여전히 유용한" 항목이 많았다. P4가 실재할 가능성은
    열렸으나, "유용해 *보임*"(회상)과 "실제로 다시 씀"(행동)은 다르다. 이 간극이 핵심.
- 그 "필요할 때"가 **도구가 감지 가능한 신호**(위치·상황)인가, **보이지 않는 내면 필요**인가?
  → 본인 답: **둘이 섞여 있다.** 그래서 이 분류 자체를 부검에서 측정한다.

## 3. 가설 스택 (위험도 순 — 위가 무너지면 아래는 의미 없음)

| ID | 가설 | 겨냥 불편 | 진짜 위험(왜 무너질 수 있나) |
|---|---|---|---|
| **H-통합** | 한 곳에 모으면 흩어짐이 해소된다 | P2 | 해법은 자명. 리스크는 *사람들이 실제로 기존 습관(카톡 나에게 2초)을 버리고 옮겨 모으나* (수집 전환 비용) |
| **H-검색** | 모아두면 필요할 때 실제로 빨리 찾는다 | P3 | *못 찾아서 아픈 순간이 충분히 자주 오나* |
| **H-재발견** ⭐ | 안 까먹게 이어주면 실제로 다시 쓴다 | P4 | **가장 불확실.** *회상 "유용해 보임"이 실제 행동으로 전환되나(collector's fallacy를 이기나)*, *리마인드가 무시·피로로 죽지 않나* |

**H-재발견이 이 아이디어 전체의 생사를 가른다.** 사람들은 이미 저장을 충분히 쉽게 하고 있고(P1은
불편 아님), 모아두는 것/찾는 것의 가치는 비교적 자명하다. 무너진다면 "다시 안 본다"는 지점에서다.

### 두 갈래 해법(테스트로 판정)
- **Path 1 — 만능 아카이버 + 리마인드:** 모든 걸 저장하고, 시간 기반으로 다시 띄움. H-재발견에 베팅.
- **Path 2 — 상황 트리거:** "필요할 때"가 감지 가능한 저장물(가볼 곳 등)만, 그 순간(위치·약속)에 소환.
  A(지금 필요)와 B(재발견)의 장점만 결합. 기억 안 나도 됨 — 트리거가 외부에 있으므로.

**지금 Path 1/2를 머리로 고르지 않는다. 둘 다 H-재발견 위에 서 있으니, 테스트가 정하게 한다.**

## 4. 검증 방법 (코드 0, 앱 이전, 총 3주)

핵심 철칙: **행동을 측정한다. 의견을 묻지 않는다.**
"유용할 것 같아요?"엔 다들 "네"라고 답하고(그리고 안 쓴다). 실제 행동만 신호다.

### ①단계 · 과거 저장물 부검 (이번 주)

- **목적:** P4가 진짜 불편인지 반증 + P3 빈도 baseline + 세그먼트(어디에 당김) + 필요순간 (a)/(b) 분류
- **참가자:** 본인 + 3~5명 (저장 습관 있는 지인. 많을 필요 없음)
- **방법:** 각자 저장처(카톡 나에게 / 인스타 저장 / 북마크)를 열고 최근 저장물 20~30개를 함께 훑으며
  스프레드시트 한 장에 기록. 1인당 30~40분, 인터뷰처럼 옆에서.

**기록 시트:**

| 항목 | 종류 | ①저장 기억했나 | ②그동안 다시 봤나(횟수) | ③필요했는데 못 찾은 적(P3) | ④지금 보니 여전히 유용/실행할 건가 | ⑤필요할 때가 (a)감지가능/(b)내면 |
|---|---|---|---|---|---|---|
| 예: 성수 OO카페 | 맛집 | N | 0 | — | Y | a |
| 예: OO 자기계발 릴스 | 자기계발 | N | 0 | N | N | b |

**뽑을 지표:**
- **까먹음율** = ①이 N인 비율 → P4 전제("까먹는다") 실재성
- **재소비율** = ②가 1회+ 비율
- **여전히-유용율** = ④가 Y인 비율
- **P3 발생** = ③ 있는 사람 비율·빈도
- **세그먼트별 재소비율/당김** = 맛집 vs 레시피 vs 자기계발 …
- **트리거 분포** = ⑤ (a) 대 (b) 비율

**판정(P4가 진짜 불편인지):**
- 재소비 낮음(②=N) & ④도 N → **죽은 데이터** = P4는 불편 아님(collector's fallacy 확정).
- 재소비 낮음 & ④=Y 多 → **"봤어야 했는데 놓친" 진짜 P4 통증** = ②단계로 갈 정당한 근거.

**①단계 진행 기준(기본값, 조정 가능):**
- "잊었지만 여전히 유용(④=Y)" 비율 **≥ 30%** → P4 통증 실재 → ②단계 진행.
- **< 15%** → 대부분 죽은 데이터 = collector's fallacy 확정 → 방향 근본 재고(또는 Path 2의 좁은 영역만).

### ②단계 · Wizard-of-Oz 리마인드 (2~3주)

- **목적:** H-재발견 검증 — 리마인드가 **실제 재소비/행동**으로 전환되나? (회상 아님, 행동)
- **참가자:** ①의 사람들 중 의향 있는 3~5명(본인 포함)
- **방법 — 사람이 "알고리즘" 역할, 앱 없음:**
  1. 참가자가 앞으로 저장하는 걸 진행자에게도 흘려보냄(카톡 포워드 or 공유 시트).
  2. 진행자가 적절한 시점에 **손으로 리마인드 메시지**를 보냄.
  3. 두 방식을 **대조:**
     - **(a) 시간 트리거:** 저장 N일 후 "지난번 저장한 [X] 다시 볼래?" ← Path 1 검증
     - **(b) 상황 트리거:** 참가자가 "이번 주말 성수 감" 같은 맥락을 주면 관련 저장물 소환 ← Path 2 검증

**리마인드마다 반응 기록(진짜 행동 데이터):**
`무시 / 열어만 봄 / 실제 행동함(갔다·샀다·요리함·실천) / "고마워" / 짜증·음소거 요청`

**뽑을 지표:**
- 리마인드 → 열람 전환율
- **리마인드 → 실제 행동 전환율** ← H-재발견의 생사
- **알림 피로 신호** — 며칠 만에 무시율 급증? 음소거 요청?
- **(a) 시간 vs (b) 상황 전환율 차이** ← Path 1 vs Path 2 판정

### 성공/중단 기준 (시작 전 못 박기 — 기본값, 조정 가능)

리마인드 → **실제 행동** 전환율 기준:
- **≥ 30%** → H-재발견 유효. Path 1(만능+리마인드) 진행 가능.
- **10 ~ 30%** → 무차별 리마인드는 약함. (b) 상황 트리거만 유효한지 재실험 → Path 2로 좁힘.
- **< 10%** → H-재발견 반증. 시간 기반 리마인드는 접는다. Path 2의 좁은 영역(감지 가능 트리거)만 검토.

피로 기준:
- 2주 내 무시율 급증 **또는** 참가자 1명이라도 음소거·중단 요청 → "무차별 리마인드" 사망 신호,
  트리거 정교화(상황 기반) 필요.

---

## 5. 이 테스트가 정해주는 것

- H-재발견이 사나/죽나 → 리마인드 기능(및 "안 본 게시글" 탭)을 지을 가치가 있나.
- (a) 시간 vs (b) 상황 트리거 → **Path 1 vs Path 2** 방향을 데이터로 결정.
- 세그먼트별 당김 → 만능이 아니라 "당김 확실한 한 종류부터" 좁혀야 하나.

**결과에 따른 분기:**
- H-재발견 유효(≥30%) → 기존 MVP(Path 1)로 진행하되, 부검에서 나온 강한 세그먼트를 온보딩 기본값으로.
- 상황 트리거만 유효(10~30% & (b)≫(a)) → MVP를 Path 2로 재설계(가볼 곳/맥락 소환 중심).
- 전면 반증(<10%) → 저장-재소비 전제 자체를 재고. 다른 불편(P2/P3만) 혹은 다른 문제로 피벗.

## 6. 결정 기록

| 결정 | 선택 | 이유 |
|---|---|---|
| 첫 산출물 | 풀 MVP가 아니라 검증 실험 | 가장 위험한 가정(H-재발견)을 가장 싸게 확인 |
| 측정 대상 | 의견이 아니라 행동 | "유용할 것 같다"는 신호가 아니다 |
| 프로토타입 형태 | Wizard-of-Oz(사람이 앱 역할) | 코드 0으로 리마인드 메커니즘을 실제로 테스트 |
| Path 1 vs 2 | 지금 안 고름 | 둘 다 H-재발견 위에 있으니 테스트가 결정 |
| 랜딩페이지 스모크 테스트 | 채택 안 함 | 가입은 의도지 행동이 아님 — 이 가설(재소비 전환)엔 부적합 |
