날짜: 2026-07-27
상태: 실행중
관계: `2026-07-20-link-moa-hypothesis-validation-design.md`(만능 아카이버 3주 검증)를
**장소 특화(Path 2) + 마감 2일** 조건으로 다시 좁힌 실전 설계.
목적: **지원사업/경진대회 제출** — 심사 3기준(타겟 정의 / 문제 검증 / 해결책 검증)을 각각 증거로 채운다.

## 0. 한 줄 요약

> 릴스로 카페·맛집을 **DM/캡쳐로 던져만 두고 정작 못 가는 20~30대**에게,
> **공유 한 번 → AI가 지도에 자동 정리**가 그 습관을 대체할 가치가 있는지,
> 마감 2일 안에 **미래 로그가 아니라 "이미 일어난 과거 행동"**으로 검증한다.

---

## 1. 타겟 정의 (심사 기준 ①)

**초기 유저 (한 문장):**
> 인스타 릴스로 카페·맛집을 습관적으로 저장하지만 정작 못 가는 20~30대 중,
> **네이버 지도 북마크는 안 쓰고** (수동 저장이 귀찮아서) 릴스를 **DM(나에게 보내기)이나 캡쳐**로 던져두는 사람.

**핵심: 포함/제외 경계가 곧 wedge다.**

| | 포함 (우리 유저) | 제외 (우리 유저 아님) |
|---|---|---|
| 저장 행동 | DM 나에게 보내기 / 캡쳐 / 릴스 저장 폴더 | 네이버 지도 즐겨찾기에 손으로 저장 |
| 심리 | "정리는 귀찮고, 일단 던져둠" | "이미 스스로 정리 체계가 있음" |
| 문제 | 던진 게 흩어져 **무덤**이 됨 → 못 감 | 문제 이미 해결됨 |

제외 집단(네이버 북마크 유저)은 이미 문제를 스스로 풀었으므로 우리 고객이 아니다.
**우리의 표적은 "저장 의지는 있으나 정리 마찰 때문에 방치하는 중간 집단"**이다.

---

## 2. 왜 이 검증인가 — 리서치가 바꾼 프레임

온라인 수요 신호 리서치(2026-07-27) 결과, 통증의 실재는 **이미 시장이 증명**했다:

- **네이버**: 장소 저장 누적 횟수 최근 1년 **2배 증가**, 저장 한도 2,000→**5,000곳** 확대,
  "방문 전 가고 싶은 곳 저장·공유" 행태 공식 확인, **저장 탭 신설 + 친구 공유** 로드맵.
  (출처: DealSite경제TV, https://news.dealsitetv.com/articles/89694)
- **직접 경쟁**: **쏙핀(SsokPin)** = "인스타·블로그 맛집을 AI가 자동 추출해 내 지도에 저장,
  링크 공유 한 번" → 장소모아와 기능 거의 동일. 그 외 Saver·뭐먹지·식후경·InSave·맛튜버맵 다수.

**함의:** 심사에서의 진짜 위험은 "이 통증이 있나?"(H1)가 아니라 **"왜 네이버·쏙핀 두고 너희냐"**다.
그래서 가설의 무게중심을 **wedge 실재(H1')**로 옮긴다.

## 3. 가설 스택 (위험도 순 — 위가 무너지면 아래는 의미 없음)

| ID | 가설 | 2일 내 검증? | 진짜 위험 |
|---|---|---|---|
| H1 통증 실재 | 릴스 저장→못 감 불편이 있다 | (네이버 데이터로 대체 입증) | 낮음 |
| **H1' · wedge 실재** ⭐ | "북마크는 안 쓰지만 DM/캡쳐는 하는" 중간 집단이 **실재하고 충분히 크다** | ✅ 인터뷰+폼 | 실은 소수거나, 결국 네이버로 흡수 |
| **H2 · 저장 전환** | 우리 방식이 DM/캡쳐 습관을 **실제로 대체**한다 | ✅ 인터뷰 중 실사용 | 쏙핀도 같은 걸 함 — 전환 차별점 약할 수 있음 |
| **H3 · 재발견→행동** | 모아두면 **실제로 간다** | ❌ (몇 주 필요) | collector's fallacy. **"다음 검증"으로 명시하고 정직하게 인정** |

**철칙: 행동을 측정한다. 의견을 묻지 않는다.**
2일 안에 구할 수 있는 유일한 진짜 행동 증거는 미래 로그가 아니라 **참가자의 과거 행동**(DM/캡쳐 무덤)이다.

## 4. 검증 방법 (3단 퍼널, 2일)

### ① 온라인 수요 신호 리서치 — 완료 (§2)
- 산출: 네이버 저장 2배↑, 한도 확대, 경쟁 지형(쏙핀 등). → 심사 "시장 존재" 슬라이드.
- 판정: 시장 존재 ✅. 남는 질문은 wedge/차별화 → ②③로.

### ② 인터뷰 + 과거 무덤 부검 (Day 1~2, 지인 4~6명 · 1인 30분)
- **문서:** `docs/validation/interview-script.md`, 시트 `docs/validation/autopsy-sheet.csv`
- **최우선 임무 = H1' wedge 검증.** "너 네이버 지도 저장 써? 안 쓰면 왜? 대신 뭐 해?"로 시작.
- **과거 부검:** 본인 인스타 DM 나에게 보내기 / 저장 폴더 / 캡쳐 앨범을 함께 열어 최근 15~30개를
  훑으며 시트에 기록. (a)규모, (b)실제로 간 곳 %, (c)저장한 것도 까먹은 % , (d)지금 봐도 가고 싶은데 못 간 %.
- **뽑을 지표:**
  - **wedge율** = "저장 던지지만 네이버 북마크 안 씀" 참가자 비율
  - **방치율(무덤율)** = 던진 것 중 실제로 간 곳이 낮은 비율 (collector's fallacy 정량)
  - **놓친-기회율** = (d) 지금 봐도 가고 싶은데 못 간 % (= 진짜 통증)

### ③ 인터뷰 말미 실사용 프로브 (H2 저장 전환)
- 같은 참가자에게 프로토타입을 쥐여주고 **방금 얘기한 릴스 하나를 실제로 저장**시킨다.
- 관찰(행동): 저장 성공했나 / 걸린 시간(초) / "DM보다 쉽다/똑같다/어렵다" / 막힌 지점.
- 라이브 웹앱 이벤트 로깅(§5)이 이 저장을 숫자로도 남긴다.

### ④ 자가진단 퀴즈 = 수요조사 퍼널 (병행, 규모 신호) — 핵심 배포물
- **라우트:** `/quiz` ("나는 어떤 맛집 저장러?" 밸런스게임형). 보조: `/lp` 랜딩, `docs/validation/google-form.md`.
- **작동:** 6문항 → 점수화 → 5유형 판정(타겟 여부 포함) → 결과 화면에서 3갈래로 흘려보냄:
  - 🌐 웹 프로토타입 바로 써보기 (`/`)
  - 🍎 iOS 베타 (TestFlight URL 있으면 링크 아웃, 없으면 이메일 수집 → 수동 초대)
  - 🤖 안드로이드 출시 알림 (이메일 수집)
- **왜 퀴즈인가:** 카톡·인스타 공유가 잘 되는 형식(바이럴) + 응답자가 스스로 타겟/비타겟을 분류해줌
  = wedge율을 **정량으로** 얻는 저비용 채널.
- **뽑을 지표(자동 집계 `/api/stats`):** 퀴즈 완료율, **타겟 유형 비율**(=wedge율 정량),
  CTA 클릭(web/ios/android), 플랫폼별 사전신청 수.
- **단 "쓰겠다는 신청"은 의도지 행동 아님 → 데크에서 보조 지표로 명시.** 진짜 행동은 ②부검 + ③실사용.

## 5. 라이브 프로토타입 이벤트 로깅 (계측)

기존 웹앱(Next.js + libsql)에 최소 계측을 붙여 인터뷰 중/배포 중 **실제 행동을 숫자로** 남긴다.

- 새 테이블 `events(id, uid, name, props, created_at)`, `waitlist(email, uid, platform, persona, created_at)`.
- `POST /api/track` — 클라이언트 이벤트: `visit`, `lp_view`, `quiz_start`, `quiz_complete`, `cta_web/ios/android`.
- `POST /api/waitlist` — 사전신청(이메일 + platform + persona).
- 서버 계측(`/api/ingest`): `save_attempt` / `save_success`(단건) / `save_pending`(대기함) / `save_fail`.
- 공유: `bundle_created`(공유 생성).
- 조회: `GET /api/stats` — 퀴즈 퍼널 + 앱 퍼널 + 플랫폼별 사전신청 집계 JSON (제출 데크 숫자용).
- iOS 베타 링크는 환경변수 `NEXT_PUBLIC_TESTFLIGHT_URL`로 주입(없으면 이메일 수집으로 폴백).

**측정 핵심 지표(퍼널):** `visit → save_attempt → save_success → bundle_created`.
저장 전환율(save_success/save_attempt), 1인당 저장 수, 공유 발생률.

## 6. 성공/중단 기준 (시작 전 못 박기 — 기본값, 조정 가능)

| 가설 | 지표 | GO | 재검토 | STOP |
|---|---|---|---|---|
| H1' wedge | wedge율(부검 참가자 중) | ≥ 50% | 30~50% | < 30% (집단이 소수 → 타겟 재정의) |
| H1' 통증 | 놓친-기회율(d) | ≥ 30% | 15~30% | < 15% (죽은 데이터 = collector's fallacy 확정) |
| H2 전환 | 실사용 "DM보다 쉽다" | 과반 | | 아무도 안 그럼 (마찰 차별점 없음) |
| — | 저장 성공률(로그) | ≥ 70% | | 잦은 실패 = 제품 완성도 문제 |

**H3(재발견→행동)는 2일 내 판정하지 않는다.** 데크에 "다음 4주 Wizard-of-Oz로 검증 예정"으로 정직하게 명시.

## 7. 제출 서사 (심사 3기준 매핑)

| 심사 기준 | 우리 증거 |
|---|---|
| ① 타겟 정의 | §1 포함/제외 경계 + wedge율(부검) |
| ② 문제 검증 | §2 시장 데이터(네이버 2배↑) + ②부검 인용·지표(방치율·놓친기회율) |
| ③ 해결책 검증 | ③실사용 저장 전환(행동) + §5 로그(저장 성공률·1인당 저장수·공유) |

**정직성 = 강점.** "만능 아카이버 → 장소 특화로 피벗" 서사와 "H3는 아직 미검증, 다음 실험 설계함"을
드러내는 것이 심사위원에게 가짜 traction보다 신뢰를 준다.

| 무게중심 | H1 통증 → **H1' wedge** | 네이버가 통증을 이미 증명, 진짜 위험은 차별화 |
